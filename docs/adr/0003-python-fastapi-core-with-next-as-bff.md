# ADR-0003: Python/FastAPI for the AI core, Next.js as the BFF

## Status

Accepted — 2026-08-29

## Context

The system has two halves with genuinely different natures:

- **AI core and domain** — case generation, the deducibility solver, dossier
  assembly, NPC orchestration, classifiers, output filters, the stance machine,
  the verdict. Every deterministic rule lives here (RN-002, RN-023, RN-032), and
  so does the isolation boundary (RN-010, RN-011).
- **Player experience** — streaming chat, the notebook, the accusation and
  replay screens. Needs a reactive UI and a fast first token.

The ecosystem that matters for the first half — validated structured output,
evaluation, tracing, agent orchestration, analysis notebooks — is overwhelmingly
Python. The ecosystem for the second is TypeScript.

One more constraint: the model provider's key must never reach the browser, and
a response has to pass the canary filter and the scope check **before** it
leaves for the client (RN-042) — including on the streaming path.

## Decision

Two applications with an explicit boundary:

- **`apps/api` — FastAPI (Python).** Owns the whole domain, every call to a
  model, and every checkpoint. No business rule lives outside it. Exposes REST
  and SSE.
- **`apps/web` — Next.js (TypeScript).** UI and **BFF**: route handlers proxy
  SSE to the browser, handle session and cookies, and aggregate calls for a
  screen. The front end never talks to the model provider or to the database.

The contract is the OpenAPI document FastAPI generates, committed as
`openapi.json`, with TypeScript types generated by `openapi-typescript` into
`packages/contracts` (ADR-0001). SSE events are documented in
`docs/asyncapi.yaml`, because OpenAPI does not describe a stream.

Which orchestration framework runs inside the core — LangGraph or something
hand-rolled — is a separate decision.

## Consequences

+ Every path with a determinism guarantee sits in one process, in one language,
  under one test suite.
+ The canary filter and the scope check live on the server side of the boundary,
  with no way for a shortcut in the front end to skip validation.
+ Evals, tracing and analysis use the same libraries as the core.
+ The front end can move to Vercel while the core runs on Magalu, with no
  rewrite.
+ Types cross the boundary: breaking the contract breaks the front-end build.
− Two languages, two toolchains, two linters, two type checkers.
− One extra network hop on the streaming path (browser → BFF → API). It costs a
  few milliseconds and requires care not to buffer the SSE in the middle.
− The domain model exists in two places (Pydantic and generated types).
  Mitigated by generation — a hand-written TypeScript type is a bug waiting.
− Deployment in two pieces, with contract versioning between them.

## Alternatives considered

- **All TypeScript (Next.js with the Vercel AI SDK).** One language, trivial
  streaming, single deployment. Rejected because of the ecosystem for the hard
  half: evaluation, the solver and trace analysis are orders of magnitude more
  productive in Python, and the project is about the hard half.
- **All Python (FastAPI with HTMX/Jinja).** Removes the boundary and the network
  hop. Rejected because the notebook and the replay are genuinely stateful
  interfaces, and because the front-end experience is part of what the project
  demonstrates.
- **Browser talking directly to FastAPI, no BFF.** One hop less, but it pushes
  CORS, sessions and screen aggregation into the domain core, and turns every
  endpoint into public surface.
